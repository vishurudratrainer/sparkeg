Monitoring an Apache Spark application using the Spark Web UI requires understanding its hierarchical execution model: **Action $\rightarrow$ Job $\rightarrow$ Stage $\rightarrow$ Task**.

---

### PySpark Example Script

To see these metrics in action, consider this PySpark job that reads data, performs a transformation, executes a wide dependency transformation (`groupBy`), and triggers an action (`collect()`):

```python
from pyspark.sql import SparkSession
from pyspark.sql.functions import col, rand

# Initialize Spark Session
spark = SparkSession.builder \
    .appName("SparkUIMetricsExample") \
    .master("local[*]") \
    .getOrCreate()

# 1. Generate a dummy DataFrame with 2 million rows
df = spark.range(0, 2000000).withColumn("value", (rand() * 100).cast("int"))

# 2. Narrow transformation (no shuffle)
filtered_df = df.filter(col("value") > 50)

# 3. Wide transformation (groupBy triggers a shuffle)
agg_df = filtered_df.groupBy("value").count()

# 4. Action: triggers Job execution
results = agg_df.collect()

print(f"Total groups: {len(results)}")
spark.stop()

```

When you run this script, open your browser and navigate to **`http://localhost:4040`** (the default Spark UI port while an application is running).

### Core Metrics Available in the Spark Web UI & What to Look For

#### 1. Jobs Tab

An execution unit triggered by an action (e.g., `.collect()` or `.count()`).

* **What to look for:**
* **Stages: Succeeded/Total:** Shows how many stages comprise the job.
* **Duration & Timeline:** Identifies how long the user action took. If a job takes unexpectedly long, click its description to inspect individual stages.



#### 2. Stages Tab (and Stage Detail Page)

A stage is a set of tasks running the same code concurrently on different partitions. Stages are divided by **shuffle boundaries** (e.g., aggregations, joins, or repartitioning).

* **Key Metrics & What to Look For:**
* **Duration:** How long tasks inside the stage took to process.
* **Task Summary Metrics (Percentiles: Min, 25th, Median, 75th, Max):**
* *What to see:* Look closely at the **Duration** and **Input Size** across percentiles. If the Median duration is 2 seconds, but the Max duration is 5 minutes, you have a **straggler task** caused by **data skew** (one partition holds much more data than others).


* **Shuffle Read Size / Records:** Total data pulled across the network from other executors during a join or aggregation.
* **Shuffle Write Size / Records:** Data written out to local disk/memory to be read by a downstream stage.
* **Shuffle Spill (Memory) & Shuffle Spill (Disk):**
* *What to see:* If data exceeds available memory during a shuffle or sort, Spark spills it to disk. **High disk spill values indicate a severe performance bottleneck**. Fix this by increasing partitions (`spark.sql.shuffle.partitions`) or giving executors more memory.





#### 3. Executors Tab

Provides cluster-wide health statistics broken down per node/executor.

* **Key Metrics & What to Look For:**
* **Task Time vs. GC Time (Garbage Collection):** If GC Time takes up a large percentage of total task time, the JVM heap is choking due to high object creation or insufficient memory.
* **Memory Used / Storage Memory:** Shows how much heap memory is currently active versus used for caching (`.cache()` / `.persist()`).
* **Failed Tasks:** If a specific executor has a high failure rate, check its logs for `OutOfMemoryError` or node hardware loss.



#### 4. SQL / DataFrame Tab

Because modern PySpark relies heavily on Catalyst Optimizer plans, this tab is essential for structured data workflows.

* **Key Metrics & What to Look For:**
* Click on your completed query to view its **Visualized Directed Acyclic Graph (DAG)** and **Physical Plan**.
* Check operator metrics like **Number of Output Rows** and **Scan Size** to see how effectively filters (predicate pushdown) are weeding out data early in the pipeline.

### Summary Checklist for Troubleshooting in the UI

1. Is a job taking too long? Go to **Jobs $\rightarrow$ Stages** and locate the bottleneck stage.
2. Is there data skew? Open the **Stage Detail** page and compare the **Min vs. Max Task Duration**.
3. Are resources running low? Check the **Executors** tab for high **GC Time** or memory exhaustion.
4. Are joins/aggregations slowing things down? Look for high **Shuffle Spill (Disk)** metrics.


Beyond Jobs, Stages, and Shuffle Spill, several other critical areas and metrics in the Spark Web UI help diagnose hidden performance degradation, resource waste, and optimization opportunities.

---

### 1. Storage Tab (Cached RDDs & DataFrames)

If your PySpark code uses `.cache()` or `.persist()` to save intermediate results, the **Storage** tab becomes essential.

* **Key Metrics to Watch:**
* **Fraction Cached:** Shows what percentage of the dataset fit into memory (e.g., `100%` or `45%`).
* **Size in Memory vs. Size in Disk:** If data exceeds available executor memory, Spark evicts cached partitions to local disk.


* **What it tells you:** If you see cached data spilling to disk, your cache is too large for the allocated executor memory. This will cause severe I/O slowdowns on subsequent actions.
* *Verification:* Ensure **Fraction Cached** reads `100%` and **Size in Disk** reads `0 B` for optimal caching performance.

---

### 2. SQL / Catalyst Optimizer Tab (Physical Plans)

Modern PySpark relies heavily on DataFrame operations optimized by the Catalyst engine. Clicking into the **SQL/DataFrame** tab reveals the underlying query execution plan.

* **Key Metrics & Indicators to Watch:**
* **Join Strategy (`SortMergeJoin` vs. `BroadcastHashJoin`):**
* If you see a `SortMergeJoin` on a large table joined with a very small lookup table, Spark is performing an expensive, full shuffle join.
* *Optimization:* For small tables, force a broadcast join using `F.broadcast(small_df)` to change it to a `BroadcastHashJoin`, eliminating the shuffle entirely.


* **Scan Size / Number of Output Rows:** Compare the number of rows scanned at the data source versus the rows output after filters. If a massive table is fully scanned before filtering, your predicate pushdown or partitioning strategy needs adjustment.


* *Verification:* Check the visual DAG for the query to ensure filters occur as close to the data source (Scan nodes) as possible.

---

### 3. Executors Tab: Task Deserialization & GC Time

The **Executors** tab provides a cluster-wide summary of CPU utilization, memory distribution, and overhead costs.

* **Key Metrics to Watch:**
* **Task Deserialization Time:** The time spent by executors sending code closures and tasks from the driver to the worker nodes. If this is exceptionally high, your closures might be capturing massive broadcast variables or large objects inefficiently.
* **Total CPU Time vs. Execution Time:** If CPU time is low while execution time is high, your application is bottlenecked by I/O (disk/network shuffling) or garbage collection rather than actual compute power.


* *Verification:* Look at the summary row for **GC Time** across executors; it should ideally remain well under 10% of total task time.

---

### 4. Environment Tab (Configuration Verification)

When tuning PySpark parameters in code (such as changing shuffle partitions or memory limits), it is easy to make syntax errors or override settings unintentionally.

* **What to look for:** Search the **Environment** tab for specific configuration keys (e.g., `spark.sql.shuffle.partitions` or `spark.executor.memory`).
* **Why it matters:** This tab lists the *actual runtime configuration values* being enforced by the Spark cluster, letting you verify whether your configuration settings were correctly applied.


To get that **"mind blown"** moment in the Spark Web UI, nothing beats demonstrating **Broadcast Hash Join Optimization**.

Normally, when you join two large datasets, Spark has to shuffle gigabytes of data across the network (a `SortMergeJoin`). But if one table is small, you can force Spark to broadcast it to every worker node, completely eliminating the shuffle. In the Spark UI, you will literally watch a massive shuffle stage vanish into thin air.

---

### The "Before & After" Code Demo

Save and run this script, which executes a standard join first, and then an optimized broadcast join:

```python
from pyspark.sql import SparkSession
from pyspark.sql.functions import col, broadcast

# Initialize Spark Session
spark = SparkSession.builder \
    .appName("BroadcastJoinWowDemo") \
    .master("local[4]") \
    .getOrCreate()

print("Spark UI available at http://localhost:4040")

# 1. Create a large "Fact" DataFrame (5 million rows)
large_df = spark.range(0, 5_000_000).withColumnRenamed("id", "user_id") \
    .withColumn("category_id", (col("user_id") % 10).cast("int"))

# 2. Create a tiny "Dimension" DataFrame (just 10 lookup rows)
dim_data = [(i, f"Category_Name_{i}") for i in range(10)]
small_df = spark.createDataFrame(dim_data, ["id", "category_name"])

input("Script paused. Open http://localhost:4040, then press Enter to run SCENARIO 1 (Standard Join)...")

# --- SCENARIO 1: Standard Join (Triggers a heavy Shuffle) ---
print("Running Standard Join...")
standard_result = large_df.join(small_df, large_df["category_id"] == small_df["id"])
standard_result.count() # Action triggers Job 1

input("Job 1 finished. Check Spark UI, then press Enter to run SCENARIO 2 (Broadcast Join)...")

# --- SCENARIO 2: Broadcast Join (Zero Shuffle Magic) ---
print("Running Broadcast Join...")
# Wrapping the small DataFrame in broadcast() tells Spark to copy it to all executors
broadcast_result = large_df.join(broadcast(small_df), large_df["category_id"] == small_df["id"])
broadcast_result.count() # Action triggers Job 2

print("Finished! Check the SQL / DataFrame tab in the Spark UI to see the magic.")
input("Press Enter to exit...")
spark.stop()

```

### What to Look for in the Spark Web UI (The "Wow" Moment)

Open your browser at **`http://localhost:4040`** and click on the **SQL / DataFrame** tab while running the script. You will see two separate queries listed. Click into each to compare their visual **Directed Acyclic Graph (DAG)**:

#### 1. Job 1 (Standard Join) — *The Heavyweight*

* **In the DAG:** You will see an **`Exchange`** node (or `SortMergeJoin`) sitting right in the middle of the graph.
* **In the Stages tab:** Look at **Shuffle Read Size** and **Shuffle Write Size**. Spark had to sort and route millions of rows across network partitions, taking several seconds and consuming I/O bandwidth.

#### 2. Job 2 (Broadcast Join) — *The Magic Trick*

* **In the DAG:** The `Exchange` node **completely disappears**. Instead, you will see a **`BroadcastHashJoin`** or **`BroadcastExchange`** operating entirely locally on each executor.
* **In the Stages tab:**
* **Shuffle Read/Write Size drops to `0 B**` (or only a few kilobytes for the tiny broadcast copy).
* **Duration** drops drastically because no data crossed the network.



This visual transformation—watching a sprawling, multi-stage shuffle collapse into a clean, lightning-fast execution plan just by adding `.broadcast()`—is one of the most satisfying things to witness in data engineering.
